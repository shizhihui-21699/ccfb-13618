# 文档重建服务（Document Rebuild Service）架构设计

## 1. 目标与威胁模型

### 1.1 要解决的问题

外部文档不直接交给员工打开，而是由本服务"重建"为一份干净的 PDF：

- **不做恶意判定**：不假设能识别毒文档，所有输入一律按"有毒"处理。
- **渲染保真**：多栏、竖排、表格、批注、表单在视觉上尽量还原。
- **文字可用**：重建后的 PDF 文字可选中、可搜索（不是纯图片 PDF）。
- **签名告知**：原文档数字签名在重建后必然失效，需明确、不可忽略地告知。
- **长文档流式**：上千页文档不能整体进内存，支持断点续做。
- **差异可量化**：重建前后的视觉差异有自动指标和报告。

### 1.2 威胁模型（最重要的一节）

**假设渲染器必然被攻破**：恶意文档利用 PDF 引擎 / LibreOffice / 浏览器的 0day，在渲染进程内获得任意代码执行（RCE）。隔离控制必须在 RCE 已经发生的前提下仍然成立。

| 攻击者能力（假设已具备） | 对应控制目标 |
|---|---|
| 在渲染进程内执行任意代码 | 进程无特权、seccomp 过滤 syscall、rlimit/cgroup 限制 |
| 尝试读取同机其他用户文档 | 沙箱内只 bind-mount 当前这一个输入文件，无任何其他租户路径；一次性沙箱，job 结束即销毁 |
| 尝试外传数据 / 回连 C2 | **沙箱无网络命名空间、无任何凭证**；输入由编排层预先落盘，沙箱不持有对象存储 token |
| 尝试内核提权逃逸 | 生产用 gVisor（用户态内核）收窄内核攻击面；最高保障级用 Firecracker microVM |
| 尝试在输出 PDF 里植入恶意内容 | 输出在沙箱外由可信校验器做对象树扫描 + 二次渲染验证 |
| 尝试通过宏 / JS 执行 | Office 宏全局禁用；PDF 的 JS/Action 不继承（图像层方案天然丢弃），HTML 的 JS 在无网络沙箱内运行且仅用于排版 |

一条核心设计原则：**渲染沙箱里没有任何值得偷的东西**——没有凭证、没有网络、没有别的文件。

### 1.3 非目标（v1 明确不做）

- 不做文档恶意性判定 / 杀毒 / DLP 内容审查（可作为旁路服务对接）。
- 不做可编辑格式互转（DOCX→DOCX 等），输出只有 PDF。
- 不保留原 PDF 的矢量内容流（理由见 §4）。
- 不做交互式表单的完整重建（v1 拍平，v2 再考虑）。

## 2. 总体架构

```
                 ┌─────────────┐
  API 请求 ─────► │  API 层      │ 鉴权、限额、密码（加密 PDF）入参
                 └──────┬──────┘
                        ▼
                 ┌─────────────┐    任务状态/检查点
                 │  编排层      │◄────────► Redis/Postgres
                 │ (orchestr.)  │
                 └──┬───────┬──┘
        预取输入到  │       │ 预签名 URL（仅编排层持有凭证）
        本地 spool ▼       ▼
   ┌──────────────────┐        每个 stage 都是一次性沙箱
   │ Stage A: 归一化   │  Office/HTML/图片 ──► 标准化 PDF
   │ (LibreOffice/    │
   │  Chromium 沙箱)  │
   └────────┬─────────┘
            ▼
   ┌──────────────────┐
   │ Stage B: 逐页渲染 │  每 N 页一个渲染子进程（pypdfium2）
   │ + 文本/结构抽取   │  输出：页位图 + span 坐标 JSON + 批注/链接元数据
   └────────┬─────────┘
            ▼
   ┌──────────────────┐
   │ Stage C: 组装     │  沙箱外、可信进程：图像层 + 不可见文本层 + 安全批注
   │ (pikepdf)        │
   └────────┬─────────┘
            ▼
   ┌──────────────────┐
   │ Stage D: 校验+ diff│ 危险对象扫描、qpdf 检查、二次渲染、SSIM/文本比对
   └────────┬─────────┘
            ▼  干净 PDF + 重建报告（签名/表单/差异/丢弃项清单）
        对象存储 / 回调
```

关键边界：**A、B 在沙箱内；C、D 在沙箱外的可信进程**。沙箱只产出"数据"（位图、JSON），永不产出可执行结构。PDF 的对象树完全由我们自己的代码生成，这是输出可信的根本保证。

## 3. 格式支持矩阵与取舍

所有支持的格式先归一化成 PDF，之后管线统一。取舍标准：Linux 上是否有成熟渲染器、渲染器是否能被有效沙箱化、格式本身的攻击面是否可控。

### Tier 1（v1 支持，主力场景）

| 格式 | 归一化方式 | 备注 |
|---|---|---|
| PDF / PDF/A（含加密 PDF） | pypdfium2 直接渲染 | 密码由 API 入参，经环境变量传递（不进 argv，避免 `ps` 泄露） |
| DOCX / XLSX / PPTX | LibreOffice headless 转 PDF | 宏执行模式强制关闭（registrymodifications 设 `MacroExecutionMode=0`），禁用首跑向导、禁用网络 |
| HTML / HTM（含 MHTML） | Playwright + Chromium headless | 离线运行：所有外部请求 route.abort，JS 仅用于本地排版，单页超时 + 内存上限 |
| PNG / JPEG / TIFF（含多页 TIFF） | 直接入图，Tesseract OCR 出文本层 | 扫描件 PDF 走同一条 OCR 支路 |
| TXT / Markdown | 先经受控模板转 HTML 再走 Chromium | 自己控制排版，攻击面最小 |

### Tier 2（v1.1，风险/复杂度较高但可做）

| 格式 | 取舍说明 |
|---|---|
| ODT / ODS / ODP / RTF / CSV | 同 LibreOffice 通道，RTF 解析器历史 CVE 不少，但沙箱模型不变 |
| DOC / XLS / PPT（97-2003 二进制） | LibreOffice 支持；二进制解析器攻击面大于 OOXML，放在 Tier 2 并在报告里标注 |
| DOCM / XLSM / PPTM | **可以收，但宏强制不执行**，报告注明"宏已剥离"；不是拒绝，因为宏不是文档的视觉部分 |
| PostScript / EPS | 唯一通道是 Ghostscript，历史漏洞极多；若做，单独 gVisor 策略 + 独立限额，v1 默认关闭 |

### 明确拒绝（v1）及理由

- **XFA 动态表单 PDF**：pdfium 不渲染 XFA，LibreOffice 支持也残缺。收到后走 LibreOffice 兜底渲染并在报告中明确标注"动态表单已拍平、交互丢失"，不承诺保真。
- **WPS 专有格式（.wps/.et/.dps 旧版）、Visio（.vsd/.vsdx）、CAD（.dwg）**：Linux 无可靠渲染器，硬做只会得到低保真结果，不如明确拒绝。
- **XPS / OXPS**：同样无成熟 Linux 渲染栈。
- **EPUB**：流式分页模型与固定页面 PDF 差异大，属于另一类产品。
- **ZIP/RAR 等压缩包、未知魔数文件**：v1 不解包（解压本身是攻击面），在 API 层拒绝并返回原因。

拒绝是显式的产品行为：返回不支持的格式清单，而不是猜测格式强行渲染。

## 4. 保真方案：双层 PDF，以及为什么不继承原内容流

### 4.1 关键取舍：光栅化 vs 矢量重放

最直观的做法是解析原 PDF 内容流、清洗后重新输出矢量 PDF。**本方案否决它**，原因：

1. PDF 内容流可携带 JavaScript、OpenAction、Launch/URI 动作、嵌入文件、RichMedia、XFA、注释里的可执行脚本——"清洗"意味着要为 PDF 规范的全部危险特性做正确的黑名单/白名单，漏一个就绕过，安全不可论证。
2. 复杂文档（透明叠加、混合模式、特性字体、CID 映射）矢量重放本身就容易失真。
3. 光栅化把上述攻击面**整体物理消除**：渲染器输出的只是像素，没有可执行结构。

代价是文字不再天然可选中——用不可见文本层补回来（见 4.2），文件体积变大（用 DPI 分级和压缩控制，见 4.4）。

### 4.2 双层结构（OCRmyPDF 已验证的工业模式）

每页 PDF = 两个内容层：

1. **图像层（可见）**：整页高 DPI 位图，多栏、竖排、表格底纹、批注气泡外观全部由像素保证 1:1 还原。
2. **文本层（不可见，Tr=3 文本渲染模式）**：按渲染引擎抽取出的每个文本 span 的真实 bbox 放置不可见文字，提供选中、搜索、复制、屏幕阅读器支持。

文本层的数据来源：

- 数字版 PDF：pypdfium2 的 TextPage 抽取字符/span 的 Unicode 码点 + bbox + 阅读顺序，**不经过 OCR，没有识别误差**。
- 扫描件 / 图片：Tesseract 5 OCR（traineddata 版本固定、哈希校验），输出带字级置信度，低置信度在报告里标注。

### 4.3 竖排、多栏、表格的具体处理

**竖排文字（中日韩竖排）**：

- 不靠字体的 WMode 重排，而是**按抽取到的字符 bbox 逐字定位**：检测连续字符的推进方向，纵向推进占主导即判定竖排，用旋转后的文本矩阵（Tm）逐字放置。
- 这样做的好处：选中和搜索与视觉位置严格对齐，不依赖目标 PDF 阅读器对竖排 writing mode 的支持差异。
- 标点压缩、叠字等竖排排版细节由图像层负责视觉，文本层只负责码点与位置。

**多栏排版**：

- 视觉由图像层保证，不存在重排错位问题。
- 文本层阅读顺序：pdfium 的 TextPage 对常见多栏给出可用的阅读顺序；v1.1 加基于 x 方向投影的分栏检测做二次修正。**搜索不依赖阅读顺序**（全文索引按字符流建），阅读顺序主要影响复制粘贴和无障碍朗读。

**表格**：

- v1 保证**视觉保真 + 单元格内文字可选中**（bbox 定位天然落在单元格区域内）。
- 表格的逻辑结构（行列合并关系）v1 不重建；v2 可选输出带 Table 标签的 PDF/A-2a，用线条投影 + 文本聚类做结构推断，作为附加能力而非默认路径。

### 4.4 DPI 与体积预算

| 档位 | DPI | 适用 | A4 单页参考体积（Flate/JPEG 混合压缩） |
|---|---|---|---|
| 标准 | 200 | 默认 | 150–400 KB |
| 高清 | 300 | 合同、图纸类 API 指定 | 400 KB–1 MB |

- 文字/线条页用 Flate（无损），照片区域用 JPEG q80；按页内容自适应选择。
- **不使用 JBIG2**：JBIG2 符号表合并有把字形认错的历史问题（pdfium CVE-2023-46361 一类），安全和 OCR 语义都不划算，二值图用 CCITT G4/Flate。
- 千页文档输出体积上限可配置（默认 2 GB），超限自动降档并在报告注明。

## 5. 特性还原细则

### 5.1 批注（Annotations）

在沙箱内用 pdfium 抽取批注的类型、作者、内容、坐标、颜色，在沙箱外由我们**重新生成**全新的批注对象（不继承原对象）：

| 原批注类型 | 处理 |
|---|---|
| Text/Highlight/Underline/StrikeOut/Stamp 等标注类 | 按原 bbox 重放为标准批注，内容文本经长度限制和控制字符清洗 |
| Link | 仅保留 `http`/`https`/`mailto` 三种 scheme 且做长度/字符校验；`file:`、`javascript:`、Launch 动作一律丢弃并计入报告 |
| FileAttachment（附件） | **一律丢弃**。嵌入文件是独立攻击面，报告列明丢弃的附件名 |
| 声音/视频/RichMedia | 一律丢弃并报告 |
| 回复线程（IRT/Thread） | v1 拍平为独立批注并保留"回复于 xx"文本前缀，v2 再保留线程结构 |

### 5.2 可填写表单（AcroForm / XFA）

- **v1 一律拍平（flatten）**：渲染外观流到图像层，表单字段的标签文字进文本层。交互能力丢失这件事写进报告（字段数、字段名清单）。
- 所有表单相关 JS（计算、校验、自动填充）不执行——视觉外观以文档自带外观流为准；无外观流的字段由 LibreOffice 兜底生成外观。
- XFA 动态表单见 §3，走兜底渲染 + 显式标注。
- v2 可选：按 widget 注释的 rect 重建无 JS 的 AcroForm 字段（仅文本框/复选框/单选），动作字典不重建。

### 5.3 数字签名（强告知需求）

检测：`/AcroForm` 中的 Sig 字段、DocMDP 转换参数、增量保存段中的签名字节范围。

处理原则：**签名物理上不可能保留**——重建产生的是全新字节流，密码学签名必然失效。告知分三处，确保无法忽略：

1. **输出报告 JSON**：`signatures[]` 列出每个签名的签名者、签名时间、来源文档中的校验状态、`status: "invalidated_by_rebuild"`。
2. **PDF 元数据 + 首页水印/戳记**："本文档由重建服务生成，原数字签名已失效，不具备原件签署效力"。
3. **API 响应字段**：`has_invalidated_signature: true`，供业务系统在展示层强制提示。

同时禁止把原文档的签名字节段以增量保存方式带进新文件（组装时全新写文件，不用 incremental save）。

### 5.4 其他元素

- **书签/大纲**：抽取标题和页码，重新生成 outline（仅 GoTo 内部跳转，丢弃远程 GoToR）。
- **元数据**：默认剥离 XMP 和 DocInfo；可按租户策略保留标题等无害字段，作者/修订记录默认不留。
- **嵌入文件、多媒体、自定义标签里的脚本**：全部不进入组装环节。
- **PDF/A**：v2 提供 PDF/A-2b 输出档位（嵌入字体、限定色彩空间）。

## 6. 隔离体系：四层纵深

单点机制都会被绕过，所以隔离是叠加的四层。生产环境推荐组合：**nsjail + seccomp + gVisor + 一次性容器**。

### L1 进程级

- 专用非特权 UID 运行渲染器，`no_new_privs`，清空环境变量（仅保留显式白名单）。
- seccomp-bpf 策略：默认 EPERM，只放渲染所需 syscall（read/write/mmap/futex/exit_group 等），拒绝 ptrace/keyctl/userfaultfd/reboot 等。
- rlimit：CPU 时间、地址空间、文件描述符、进程数、文件大小全部封顶；cgroup v2 再设 `memory.max`、`cpu.max`、`pids.max`（双保险，rlimit 在部分 allocator 路径下可被绕过）。
- 渲染器以 `python -I` 启动（隔离模式：不读 `PYTHONPATH`、不把 cwd 放进 `sys.path`），防止输入目录里的冒名模块（`json.py` 之类）被 import。

### L2 OS 命名空间级（nsjail；开发机可用 bubblewrap / macOS sandbox-exec）

- mount ns：chroot 到精简 rootfs（只含渲染器和运行时库），输入目录**只读 bind-mount 且只含当前 job 的那一个文件**，输出目录挂 tmpfs，其余路径不可见。
- net ns：新建网络命名空间，不建 veth、不拉起 lo 之外的接口——**沙箱内没有网络栈可用**。
- pid/ipc/uts ns：看不到宿主进程，hostname 随机化。
- `--mode once`：每个 job（长文档每 N 页的 chunk）起一个新 jail，退出即销毁，不复用。

### L3 内核攻击面（生产关键层）

渲染器 RCE 之后的下一步通常是内核提权，这一层专门挡它：

- **gVisor（推荐默认）**：K8s 上用 runsc 运行时，系统调用由用户态 Sentry 拦截实现，容器内代码接触不到宿主内核的驱动/文件系统代码。代价是 ~5-15% 性能损耗和个别 syscall 不兼容（需在测试期固化镜像）。
- **Kata Containers / Firecracker（最高保障级）**：硬件虚拟化边界，microVM 内再套 nsjail。适合"强对抗输入"租户（如公开投递入口），冷启动和密度成本更高。
- 明确不推荐：裸 Docker 的默认共享内核容器作为唯一边界——它不是恶意代码沙箱。

### L4 编排与凭证边界

- 沙箱**不持有任何凭证**：编排层用预签名 URL 把输入预取到本地 spool，沙箱只拿到一个文件路径；输出写 tmpfs，由编排层回收后上传。
- 网络默认拒绝在网络策略层再做一遍（Namespace/NetworkPolicy 出口白名单只给编排层 Pod，渲染 Pod 无任何 egress 规则）。
- 一次性 ephemeral 容器，job 结束销毁；同一渲染节点不混放多租户的活跃 job（调度器按 tenant 池亲和，或直接每 job 独立容器）。
- 镜像最小化（distroless + 渲染器），渲染器版本固定 + 镜像签名，不装 shell 和包管理器；漏洞公告订阅 pdfium/LibreOffice/Chromium，月度滚动升级 + 紧急升级通道。

### 6.1 各渲染器的专项硬化

- **LibreOffice**：`-env:UserInstallation=file:///tmp/lo-profile`（tmpfs 独立 profile），registrymodifications 预置 `MacroExecutionMode=0`、`DisableFirstRunWizard`、禁用 `sun.net.ftp/http` 客户端；单实例模式关闭，每 job 新进程；转换超时强杀。
- **Chromium**：headless=new，`--disable-features=...` 关掉媒体/ WebGPU / WebRTC，Playwright route 层 abort 全部外部请求（即使网络命名空间失效也不联网，双保险），`--js-flags="--max-old-space-size=..."`，页面超时 + 渲染超时双计时。
- **pdfium（pypdfium2）**：自定义只读文件加载接口（`FPDF_LoadCustomDocument`），不开增量加载之外的任何回调；JBIG2 解码器禁用。
- **Tesseract**：固定 traineddata 路径与哈希，禁网络相关功能，单页超时。

## 7. 上千页文档的流式处理

### 7.1 管线流式化

- **不全量加载**：pdfium 通过自定义文件访问接口按需读取对象；编排层按页区间调度，内存中同时存在的页位图有界（信号量控制，默认 ≤ 8 页）。
- **chunk 调度**：每 25 页一个渲染子进程（一个新 jail）。理由：① 渲染器长期运行的内存累积/碎片化被周期性回收；② 崩溃的爆炸半径只有一个 chunk，重试成本小；③ 检查点粒度细。
- **组装增量追加**：pikepdf 按页 append 到目标 PDF 并定期落盘，spool 目录承载中间态，内存不累积。
- **背压**：渲染快于组装/上传时，位图先落 tmpfs/spool，spool 超水位（默认 5 GB）阻塞调度，保证磁盘不被打穿。
- **Office 类的限制**：LibreOffice 转换不是流式的，必须整体转成 PDF（独立 Stage A 沙箱，内存/超时限额单独配置），转换完成后才进入流式逐页阶段——这个限制如实写进容量规划。

### 7.2 检查点、重试与部分失败

- 任务状态存 Redis/Postgres：`{job_id, chunk_index: {status, page_range, artifact_keys}}`，worker 崩溃后新实例从最后一个完成的 chunk 续做。
- chunk 失败策略：全新沙箱重试 1 次；仍失败则标记该页区间失败。
- 交付策略可配置：默认**整单失败**（安全场景宁可不给），可选**部分交付**（成功页正常组装，失败页放错误占位页 + 报告列明页码和原因）。
- 单页渲染超时（默认 30s）、单 job 总墙钟（默认 30 分钟）、输出大小上限三层熔断。

## 8. 视觉差异自动量化

差异度量在 Stage D（可信侧）进行，输入是"原文档在我们自己渲染器下的参考位图"和"输出 PDF 的再渲染位图"。注意：**比对的是两次渲染结果，不是原件与输出**——原件本身没有规范位图，这也是唯一可自动化的基线。

### 8.1 指标集

| 指标 | 方法 | 用途 |
|---|---|---|
| SSIM | scikit-image 逐页计算（0–1，1 为完全一致） | 主指标，结构相似度，对抗锯齿轻微偏移不敏感 |
| 阈值化像素差占比 | 灰度差 > 12 的像素比例 | 直观看得出的差异有多少，过滤亚像素噪声 |
| MAE（降采样后） | 先缩到 1/4 再算平均绝对误差 | 抑制抗锯齿导致的假性差异 |
| 布局 bbox IoU | 抽取两侧文本/线条 bbox 集合做匹配 | 发现整栏丢失、表格错位这类结构性问题 |
| 文本 CER/WER | 输出 PDF 抽取文本 vs 原文档抽取文本 | 验证文本层完整性，防止"看着对、搜不到" |
| 差异热图 | 差异像素染红的旁路 PNG | 人工复核用，不进输出 PDF |

### 8.2 判定策略与校准

- 默认门槛：每页 SSIM ≥ 0.99 且像素差占比 ≤ 1%；任一不达标页标记 `visual_diff_flag`，报告逐页列出指标。
- 门槛必须用**黄金文档集**校准：建一批覆盖多栏/竖排/表格/批注/表单/透明叠加的样本，跑基线分布后再定阈值，避免凭感觉设线。
- 已知系统性偏差来源（字体替换、抗锯齿、JPEG 压缩）在报告中与"真实内容差异"区分：结构性指标（bbox IoU、CER）劣化才阻断交付，纯压缩噪声只记录。
- 报告产物：`report.json`（机器读）+ 热图 ZIP（人工抽检）+ API 汇总字段（最大/平均 SSIM、劣化页清单）。

## 9. 输出校验（可信侧，Stage D）

输出 PDF 由我们自己生成，但仍按"不信任中间产物"来校验：

1. **对象树危险键扫描**（pikepdf 遍历全部间接对象）：出现 `/JavaScript`、`/JS`、`/AA`、`/OpenAction`（非 GoTo）、`/Launch`、`/EmbeddedFiles`、`/FileSpec`、`/RichMedia`、`/Movie`、`/Sound`、`/GoToR`、`/SubmitForm`、`/ImportData` 即拒绝交付。
2. **结构检查**：qpdf `--check`（通过 pikepdf 底层）、页数与源文档一致、每页都有图像 XObject 和文本内容流。
3. **二次渲染**：用渲染器把输出 PDF 再渲染一遍，确认不会崩溃、不触发异常路径。
4. **体积/页数上限**、禁止增量保存段（确认无残留原字节）。
5. 校验失败一律不交付，转人工队列并保留全部审计日志。

## 10. 服务接口与部署形态

### 10.1 API（异步任务模型）

- `POST /jobs`：提交（预签名上传或对象存储 key）、格式、DPI 档位、加密 PDF 密码（独立字段，传输后仅落内存）、部分交付开关。
- `GET /jobs/{id}`：状态、进度（已完成页/总页数）、各阶段错误。
- `GET /jobs/{id}/result`：输出 PDF 预签名下载 + `report.json`。
- 报告固定包含：格式与归一化路径、签名失效清单、表单/批注/附件丢弃清单、逐页 diff 指标、沙箱执行审计（stage、耗时、退出码、重试次数）。

### 10.2 部署

- K8s：编排层 Deployment（持凭证）+ 渲染层 gVisor RuntimeClass 的 Job/Pod（无凭证、无 egress），队列用 Redis Streams 或 RabbitMQ，对象存储 S3 兼容（MinIO/AWS S3）。
- 本地开发：bubblewrap（Linux）或 `sandbox-exec`（macOS）提供等价策略 profile，配置同一套声明式沙箱描述，避免"开发环境裸奔"。
- 可观测：structlog 结构化日志（不记录文档内容/密码）、Prometheus 指标（每格式耗时分布、沙箱杀进程数、diff 劣化率、重试率）、渲染器崩溃单独告警（可能是在野利用尝试）。

### 10.3 技术选型清单

| 角色 | 选型 | 理由 |
|---|---|---|
| 语言/运行时 | Python 3.12 + asyncio，Pydantic 配置，structlog | 团队要求 Python；CPU 密集渲染都在 C++ 引擎子进程里 |
| PDF 渲染/抽取 | pypdfium2（pdfium） | 浏览器级引擎、内存安全记录相对好、自定义 IO 支持流式 |
| PDF 组装/校验 | pikepdf（qpdf） | 对象级操作能力强，适合危险键扫描和受控组装 |
| Office 归一化 | LibreOffice headless | Linux 上唯一全覆盖且可离线宏禁用的方案 |
| HTML 归一化 | Playwright + Chromium headless | 路由拦截可强制离线，沙箱配套成熟 |
| OCR | Tesseract 5 | 开源、可固定模型版本；OCRmyPDF 的模式作参考 |
| 图像处理/差异 | Pillow、numpy、scikit-image（SSIM） | 标准栈 |
| L2 沙箱 | nsjail（生产 Linux）/ bubblewrap（轻量）/ sandbox-exec（mac 开发） | 声明式、生产使用久 |
| L3 沙箱 | gVisor 默认，Firecracker 高保障级 | 收窄内核攻击面 / 硬件隔离 |
| 队列/状态 | Redis Streams + Postgres | 检查点与审计落库 |

## 11. 关键待验证假设（立项后先做 Spike）

1. pdfium 对中日韩**竖排**字符 bbox 的实际质量——用 30+ 份真实竖排文档测逐字定位偏差，这是文本层方案的最大不确定性。
2. LibreOffice 宏禁用配置在升级后的持久性（registrymodifications 模板要进 CI 断言）。
3. gVisor 下三个渲染器的 syscall 兼容性清单和真实性能损耗（预估 5–15%，需实测千页文档端到端时长）。
4. 200 DPI 下复杂矢量/小字号页面的 SSIM 基线分布，据此定 diff 门槛。
5. XFA 文档在 LibreOffice 兜底路径下的失真程度，决定拒绝还是兜底+标注的边界。
6. 千页 XLSX（LibreOffice 整体转换）的峰值内存，决定 Stage A 限额和并发度。

## 12. 里程碑建议

- **M1（4 周）**：Spike 清单全部出结论；单格式（PDF→PDF）端到端打通 nsjail 沙箱 + 双层组装 + 校验。
- **M2（4 周）**：流式 chunk 调度、检查点重试、diff 报告；Office/HTML 归一化接入。
- **M3（3 周）**：gVisor 部署、批注/表单/签名完整策略、审计与指标、黄金文档集与门槛校准。
- **M4（持续）**：v2 项（PDF/A、表格标签、表单字段重建、PS 通道）、红队对抗演练（重点验证 RCE 后的数据/网络隔离）。
